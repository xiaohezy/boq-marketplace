# 架构蓝图：单文件 HTML + 云服务

## 为什么是这个架构

实测结论：一个 3900+ 行、7 表、三角色、双语、含 AI 解析的业务平台，可以装在**一个 index.html** 里稳定运行。
优势：无构建步骤（改完直接发布）、无依赖地狱、AI 辅助修改时上下文集中、天然单点真相。
代价：>5000 行后导航变难——用严格的分区注释纪律对抗。

## 文件分区纪律（自上而下）

```
<style>      设计令牌（颜色/圆角/间距变量）→ 组件样式 → @media 640px 移动端块
<body>       authView（登录/注册/忘记密码）→ appView（顶栏+页签+各 page div）→ modalRoot
<script>     ① 常量与字典（状态映射/优先级/品类/里程碑）
             ② SDK 初始化与会话（boot）
             ③ 演示/预览数据（预览模式兜底，明确标注）
             ④ 工具函数（esc/fmtTime/parseLog/toast/errMsg）
             ⑤ 数据加载（loadTasks/loadSuppliers/...）
             ⑥ 各页面渲染（每页一节注释分隔）
             ⑦ 弹窗流（详情/派单/比价/定标）
             ⑧ 账号角色体系（日志状态机）
             ⑨ AI 解析链路（提示词/分批/合并/体检）
             ⑩ i18n 词典与引擎（最后，便于追加词条）
```

纪律：新功能先进对应分区；>200 行的功能块拆子函数；DOM id 全局唯一且见名知义。

## SDK 初始化与 boot 顺序

```js
const cloud = createWorkBuddyCloud({ endpoint: "https://<app>.app.workbuddy.host", publishableKey: "wbpk_..." });
// boot 顺序（错一步全乱）：
// 1. cloud.auth.getSession() 恢复会话
// 2. getUser() 补 email（部分版本 session 里没 email，实测登录根因之一）
// 3. 加载基础缓存（tasks/suppliers/models）
// 4. 角色判定（日志状态机折叠）→ staff / supplier / blocked(gate)
// 5. 渲染对应视图；任何一步失败给可操作的报错，不留白屏
```

- **预览模式**：file:// 或无会话时进入"预览模式（未登录）"，演示数据兜底，明确横幅提示——平台可以裸奔演示给任何人看。
- 本地 file:// 调试：必须触发一次登录流程才会引导数据（实测怪癖）。

## i18n 引擎（双语平台）

- translateDom 走**文本节点精确全串匹配 + 冒号前缀匹配**。
- 陷阱：拼接文本节点（"email · 管理员"）匹配不到词条——**把可翻译片段拆成独立文本节点/span**。
- 动态拼接的业务字符串（含变量）不进词典；词典只放静态 UI 文案，放 `<script>` 最后一节便于追加。

## 报错中文化（errMsg 映射）

云服务的英文报错（限流/无效码/唯一约束）必须映射成用户能懂的中文：
- 限流 →「同一邮箱每分钟最多 1 条，请静置 15 分钟（期间不要再点发送）」——**解释机制**，否则用户越点越卡。
- 无效码 →「请用最新收到的那一条（之前发送的会自动作废）」。
原则：每条报错都给"现在该怎么办"，不给死胡同。

## 移动端策略

- 不做 App：响应式网页，微信内直接打开。一期仅邮箱认证。
- @media 640px 一个块集中管理；宽表采用**双渲染**（桌面 `<table class="desktop-only">` + 手机 `.item-cards`），比强行压缩表格可读性高一个量级。
- 关键操作条手机端吸底（position:sticky bottom:0）全宽大按钮，拇指可达。
