# SaaS 平台创立蓝图（0 → 上线 → 验收跑通）

## 核心认知（实战经验）

- **瓶颈不在功能，在"跑通"**：登录、权限、审批、留痕这些"无聊"环节才是平台能不能用的分水岭。先跑通最小闭环，再加业务功能。
- **单文件 HTML + CDN SDK + 云服务**是单人/小团队的最优架构：无构建步骤、改完就发、域名固定。验证过支撑 3900 行、7 张表、三角色门户的完整业务平台。
- **验收先行**：功能上线不等于能用。用浏览器自动化把每个角色的每条链路真点一遍（配合 `platform-acceptance-browser` 技能），比人肉测试快且留证。

## 何时使用

- 从零新建带「登录 + 角色权限 + 数据库 + 审批/流转 + 在线协作」的业务平台
- 把本地脚本/Excel 流程升级为多人在线系统
- 复制已有平台模式到相邻业务（换数据模型，架构照搬）

## 五阶段路线

1. **架构定型** → `references/architecture-blueprint.md`
   单文件结构分区、SDK 初始化、会话启动流程（boot 顺序决定一切）。
2. **数据模型与 RLS** → `references/data-model-rls.md`
   表设计套路、RLS 两道门（GRANT + POLICY）、跨角色可见性函数、审计留痕表。
3. **账号与角色体系** → `references/code-skeleton.md`
   登录（验证码+密码双通道）、申请-审批状态机（日志驱动免建表）、门户自动绑定、i18n、报错中文化。
4. **发布与保域名** → `references/deployment-and-acceptance.md`
   复用 appId 发布、整目录上传纪律、用户文件不入发布目录。
5. **自动化验收** → 同上 + 外挂技能 `platform-acceptance-browser`
   七条铁律、OTP 文件握手、视觉通道、验收报告模板。

## 关键设计决策（先想清楚再动手）

| 决策点 | 推荐 | 理由（实测） |
|---|---|---|
| 架构 | 单文件 HTML + CDN SDK | 无构建、改即发；>4000 行仍可控（分区注释） |
| 认证 | 邮箱验证码 + 密码双通道 | 验证码首登设密码，后续密码登录（自动化验收可绕过 OTP） |
| 角色 | 日志状态机（task_id=0 的账号日志） | 免建账号表，申请/批准/停用全靠日志折叠，天然留痕 |
| 门户绑定 | 档案表 contact=登录邮箱 | 供应商注册后自动绑定，无需人工关联 |
| 权限 | RLS 双门 + SECURITY DEFINER 可见性函数 | 客户端不可能绕过；非供应商看全部、供应商只看派给自己的 |
| 审计 | task_logs（仅 SELECT+INSERT 授权） | 所有动作 insert-only，状态机可重放 |
| 发布 | 固定 appId 复用发布 | 保住域名与已分发链接 |
| 历史数据 | 资产化管线灌底座表 | 一次抓取多次复用（extract→结构化→缓存→入库，见骨架⑥） |
| 移动端 | 响应式 + 关键页双渲染（桌面表/手机卡） | 不做 App；微信内直接开网页 |

## 边界

- 云服务一期仅邮箱认证；微信登录/小程序需另开通道，当前架构不支持，不要承诺。
- 数据库变更走服务端 SQL（migrate 工具），应用代码不跑 DDL。
- 蓝图给的是"经过验证的最小正确路径"，不是唯一路径；偏离时说明理由。
